SVG Diagram Style Guidev1.0

Design blueprint for layered architecture diagrams in SVG.

Usage: this page is the spec that AI agents read when generating or editing SVG diagrams. Treat the tables, rule lines, and code blocks as the source of truth; every code block is the exact markup of the demo beside it (ids, coordinates and colors included); the demo canvas's white background rect and context-only elements are implicit from §1. Rendered demos are the human reference for reviewing changes with an agent. When the spec and a demo disagree, the spec wins — and the demo must be fixed to match.

1. Canvas & Background

  • viewBox = final pixel size; shared font stack on the <svg> root.
  • Background: solid #ffffff covering the full canvas.
  • Title: 26 px / 700 / #0f172a, centered, y = 40. Subtitle: 14 px / #475569, y = 64.

2. Color Palette

Tailwind-derived. One accent hue per tier; five shades per hue:

  • Accent — strokes, tier labels, markers (e.g. #8b5cf6)
  • Light fill — box fill (e.g. #f5f3ff)
  • Dark text — box titles (e.g. #4c1d95)
  • Mid text — body lines (e.g. #6d28d9)
  • Chip text — pill labels, one shade darker than mid (e.g. #5b21b6)
  • Glyph fill — mini-glyph fills (§4.6, §4.7) one step darker than the box light fill, e.g. #bfdbfe blue · #a7f3d0 green · #ddd6fe violet · #99f6e4 teal · #a5f3fc cyan · #fde68a amber

Nine roles. Titles 700, shape labels may use 600, everything else 400. Only tier labels are uppercase + letter-spaced. Escape & as &amp;; · is the list separator; version notes go in a smaller muted <tspan>.

4.7 Service-type glyphs

  • The glyph sits at box left + 20 (the standard inset); the title and all body lines share one x = box left + 46.

5. Connections & Arrows

5.1 Arrow markers

Define one marker per stroke color in <defs>, markerUnits="userSpaceOnUse". Numbered flow arrows are always slate #475569 — the numbered badge carries the step color. Colored lines (with a matching-color marker) are reserved for non-numbered special links, e.g. a sync or query path.

5.3 Connection rules

  • All connector strokes are 2 px; default color #475569.
  • Straight lines only, or right-angle elbow <path>s — no diagonals between tiers.
  • Arrows start 2–4 px after the source edge and end so the arrowhead tip lands 4–6 px before the target edge.
  • Endpoints must land on a box edge. For a horizontal arrow, its y must lie inside the vertical range of both the source and the target box (a panel edge counts as its box's edge). Never end in a gap between boxes or outside a container — check every arrow's endpoint against the box coordinates before drawing.
  • Gaps smaller than 14 px: see 5.4.
  • Vertical arrows entering a tier must not cross its label text: place the line's x beyond the tier label's text end + 8 px.
  • Clean corridors: a vertical arrow's x must pass no box, no horizontal connector and no text from source to target. A horizontal connector spanning a gap makes that gap an invalid corridor at every height. If no clean corridor exists, in order: (1) move the arrow to another corridor, (2) reroute the crossing connector as an elbow around the corridor, (3) demote the secondary relationship to a text note inside a box, (4) last resort one orthogonal line-line crossing that touches no label, badge or box edge.
  • Arrow labels: one per arrow, 11.5 px. Color: #475569 for slate lines; for a colored line, use that tier's mid-text color (e.g. #6d28d9 on the violet sync link). Vertical line → label at the line's midpoint, 14 px to the right (left if the right side is occupied). Horizontal line without a badge → label centered above, 10 px up. Horizontal line with a numbered badge → label to the left of the badge, text-anchor end at badge x − 20, 10 px above the line; the label must fit in the gap left of the badge. Format: action · :port when a port is involved. Labels must not cross box edges or the tier-label band. A label needs ≥ 16 px of free room around it; if the gap is narrower, widen the gap — never shrink the font.
  • Internal count markers (e.g. “×3 instances”) reuse the badge style in violet.

5.4 Very short gaps

  • Gap ≥ 14 px: normal arrow with offsets and clearance.
  • Gap 8–13 px: plain 2 px line, no marker — a short tick reads as direction by position alone.
  • Gap < 8 px: no connector. Boxes that close read as one unit; if they are one component, merge them and use a hairline divider inside.
  • Layout first: if two boxes exchange traffic, give them a ≥ 16 px gap so a real arrow fits.

Structure order (top → bottom): title block → client tier → core tier (tallest) → data tier → execution tier → legend. Cross-cutting concerns (auth, logging) go in the side bar. Draw order: background → tiers → boxes → text → arrows last.

One accent hue per tier. Components sharing a tier share its hue and differ by stroke style (solid / dashed / thicker) — never by color.
Fill the row. Boxes in a tier row span the tier's inner width or tile it with the standard gap — no dead zone wider than one standard gap, except a routing lane. Re-check after edits: deleting, moving or resizing an element (including adding/removing a body line) invalidates the gaps and heights around it; re-verify every affected gap, box height and tier height before finishing. The same arithmetic applies when generating a diagram from scratch.

8. Adapting the System

Swapping a tier's accent color

  • Pick a Tailwind 500- or 600-shade hue (e.g. #059669, #0891b2, #7c3aed — all 600).
  • Derive the shades from the same hue: 50/100 for fills, 700–900 for titles, 600–700 for body text, 500–600 for accents and strokes (see the §2 table).
  • If a colored marker or numbered badge exists for this tier, recolor them too.
  • Keep neutrals unchanged — the tier system stays readable as long as fills stay light (50–100) and text stays dark (600–900).

Adding a tier

  • Insert a new container between existing tiers; re-flow the 16 px gaps.
  • Grow the canvas viewBox height by the tier's height + 16, and move all tiers below it down by the same amount (including the legend).
  • Give the new tier an unused hue from the palette table.

Choosing a hue for a new tier

  • Blue = users/inputs, violet = control/core, amber = data/storage, green = compute/execution, rose = security.
  • Reserved spares: cyan #0891b2, teal #0d9488, indigo #6366f1, slate #64748b (neutral components).
  • Never reuse a hue already used by another tier in the same diagram.

Sequence / request–response diagrams (two hosts)

  • Hosts are panels (one box per host, §10.2) on the left and right; the gap between them is the network path.
  • One arrow per step, between the two panels' side edges; steps read top-to-bottom and are numbered with badges.
  • Every numbered step gets a distinct badge hue: tier accents first, then the reserved spares (cyan, teal, indigo). Never repeat a color within one diagram.
  • Space arrows ≥ 22 px apart so each line, badge and label clear the neighboring lines.
  • Inner boxes inside each panel describe the stack (layers, ports); arrows target the host panel, and the label carries the step semantics.

10.3 Common mistakes (final check)

  • Diagonal arrows — use straight lines or right-angle elbows only (§5.3).
  • Two hues in one tier — components in a tier share its accent and differ by stroke style, never by color (§7).
  • Full-opacity strokes on light boxes — standard boxes at 0.4–0.6, hero boxes 0.7–0.8 with 1.5 px; full opacity is for arrows and markers only (§2).
  • Arrow or label crossing tier-label text — route the line's x beyond the label's text end + 8 px (§5.3).
  • Arrow label touching its own line or badge — use the exact §5.3 offsets (badge x − 20, line y − 10); check every label, not just the first.
  • Empty space — after any layout or content change, re-run the §7 checks: row filled, gaps uniform, container height fits content.
